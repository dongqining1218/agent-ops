# Agent 自动化调度中台 —— 需求分析与 MVP 方案

> 输入文档：数字生命卡兹克《折腾了整整1年，毫无保留地分享一下我这套Agent自动化系统》（2026-11-02）
> 本文目的：把文章里的"个人玩法"还原成一套**可施工的工程系统**，明确我们要做什么、先做什么、不做什么。

---

## 0. 一句话结论

文章表面在讲"我怎么用 Agent"，实质在讲一件事：

> **把任务的起点从人身上移走。** 让事件触发 Agent，让 Agent 自己干，只把真正需要人拍板的那一小部分，做成一张卡片递到人面前。

所以我们要建的项目**不是又一个 Agent**，而是夹在"事件源"和"Agent"之间的那一层操作系统，由四块拼成：

| 模块 | 一句话职责 | 文章里的叫法 |
|---|---|---|
| **A. 事件中台** | 所有信号统一进来，统一鉴权/去重/路由/排队/派单/收结论 | Agent 自动化中台 |
| **B. 执行层** | 把任务变成一次真实的 Agent 运行，按 SOP 干活 | 接单程序 + Skill |
| **C. CI 中台** | 把 Agent 的产出审查、检查、合并、发布、核实 | CI 中台 |
| **D. 审批通道** | 只把必须人决定的事做成卡片，点一下就是决策 | 飞书批奏折 |

核心命题只有一句：**人的注意力是最贵的资源，系统要围绕"不要打扰我"来设计，而不是围绕"能力多强"来设计。**

## 1. 先对齐文章的方法论内核

不要照抄架构图，先抄它的**设计原则**——这些才是可迁移的。

### 1.1 三个类比，对应三个设计决定

| 类比 | 文章含义 | 落到设计上 |
|---|---|---|
| 朱元璋废丞相 | 所有事都直通本人 = 必然崩溃 | 必须有**分级授权**：Agent 能自己处理的，不许上报 |
| 票拟 / 批红 | 内阁写建议，皇帝红笔一批 | 上报物必须是**带建议和选项的决策卡片**，不是"出问题了"的裸告警 |
| 带团队 | 好团队自己推进，只报拍板项 | 上报需要**白名单**，不是"看情况" |

### 1.2 七个反直觉但关键的设计（文章的精华）

1. **事件统一格式**：来源五花八门，但进入中台一律压成一条极短的消息：`来源 / 类型 / 对象 / 一句话摘要 / 回原处的链接`。格式统一了，后面路由才有得谈。
2. **规则外置**：所有调度规则写在 `rules.json`，加一种新事件 = 加一条规则，**不改代码**。换模型也只是改一行字。
3. **拉模式（长轮询领活）**：中台推不进内网机器，就反过来——每台执行机常驻接单程序，一次最长挂 50 秒等活。机器不用暴露公网，实时性接近推送。
4. **中台只调度，不干活**：业务判断全部沉到 `skill`（给 Agent 用的 SOP），与调度解耦。改业务改 skill，不改中台。
5. **去重是第一公民**：网络抖动、用户补一句话、补一张图，都会产生重复事件。不去重 → 同一件事多个 Agent 同时在干 → 互相覆盖，必然混乱。
6. **唯一上报出口**：所有 Agent 要找人，只走同一个渠道（他的小卡），且规则里写明"只在必须决策时才说"，绝不让各路脚本把飞书刷屏。
7. **人的决定必须沉淀成资产**：`定了的事` / `定了不做的事` 两个文件，带原话和日期。我定过一次的，Agent 不许问第二遍。**这一条是整套系统长期不打扰人的根本。**

### 1.3 一个必须指出的陷阱

文章的系统**高度绑定作者个人环境**：两台 Mac Mini、本地登录好各种账号的 Chrome、飞书身份、独立开发、在北京。这不是通用架构，是"在他的约束下的最优解"。

> 我们要抄的是**不变量**（事件驱动、规则外置、拉模式、去重、决策沉淀、单一出口），
> 而不是**实现**（哪台机器、哪个 IM、哪个模型）。

另外：文中的模型名（Opus 5.5 / GPT-6.1 Sol / Terra）是作者当时的配置。**规则里不要硬编码模型名**，要留 `model` 字段，随时换。

## 2. 系统拆解：模块 A —— 事件中台（核心，第一优先）

这是整个项目 80% 的价值所在，也是**唯一必须自建**的部分。

### 2.1 处理流水线

```
事件源 ──POST /events──▶ 鉴权 ──▶ 去重 ──▶ 匹配规则 ──▶ 排队(并发/同subject串行) ──▶ 派单
                                                    │
                                              (无规则 → 只记录，不派)
                                                                              │
     执行机 ──长轮询 /lease──▶ 领任务 ──▶ 干活 ──▶ /conclude 回写结论 ◀────────┘
                                                                              │
                                    没跑成 ──▶ 退避重派(≤3) ──▶ 仍失败 / 掉线 ──▶ 上报人
                                                                              │
                                    需要人定 ──▶ 决策卡片 ──▶ 人点 ──▶ 决定变成新事件，回流中台
```

### 2.2 统一事件格式（最小契约）

```jsonc
{
  "idempotency_key": "virxact-hub:feedback.new:12",  // 去重靠它
  "source": "virxact-hub",        // 谁发来的
  "type": "feedback.new",         // 什么类型
  "subject": "feedback#12",       // 对象是谁（同一对象默认串行）
  "summary": "同事又提了一条新意见",  // 一句话，给人和 Agent 看
  "link": "https://.../feedback/12", // 回到原处
  "payload": { }                   // 原始事件（排查用）
}
```

### 2.3 规则模型（rules.json）

```jsonc
{
  "中台意见": {
    "when": { "source": ["virxact-hub"], "types": ["feedback.new", "feedback.followup", "feedback.decided"] },
    "to":   { "agent": "claude-code", "cwd": "~/code/work/virxact-hub", "skill": "hub-feedback", "model": "opus" },
    "ask":  "按其中「被 Agent 自动化中台叫起来的」一节处理。",
    "group": "hub-feedback",   // 同组内并发控制
    "parallel": 3,             // 最多 3 条同时跑
    "tell": "needed"           // needed = 需决策才找我；silent = 别烦我
  }
}
```

### 2.4 状态机（后端的心跳）

```
queued → leased → running → concluded
                    ├→ failed → retry(n≤3, 指数退避) → 仍失败 → escalated(人)
                    ├→ timeout(心跳丢失) → 重派
                    └→ need_decision → waiting_human → decided → 生成新事件回流
```

### 2.5 这一模块的技术难点（别低估）

| 难点 | 正确做法 | 常见踩坑 |
|---|---|---|
| 幂等 | `idempotency_key` 唯一索引 + 时间窗 | 只在内存去重，重启就重复派 |
| 同对象串行 | 按 `subject` 加锁/队列 | 同一意见 3 个 Agent 同时改 |
| 超时/掉线 | 心跳 + lease 到期自动回收 | 任务卡在 running 永远不动 |
| 重试风暴 | 重派上限 + 退避 + 熔断 | Agent 挂了 20 个任务同时重试 |
| 结论回写 | `/conclude` 幂等 | 重复 conclude 覆盖正确结论 |

### 2.6 顺带获得的东西（不要当副产品）

- **全量留痕**：每件事什么时候来、谁派的、哪个 Agent、结论是什么、怎么解决的。点开能跳回当时的会话。
- **数据沉淀**：哪条流水线最忙、哪个 Agent 干得最多、哪类事老出问题 → 以后换模型/改规则有依据。
- **可视化**：流水线像游戏一样展示（作者的"自动化小镇"）。**很好，但必须后置，不在 MVP。**

## 3. 模块 B —— 执行层（接单程序 + Skill）

### 3.1 接单程序（worker）

职责极简，三段：**长轮询领活 → 起 Agent → 回写结论**。

```
loop:
  task = POST /lease?agent=m4-codex&ttl=50s   # 挂 50 秒，没活就再挂
  if task:
      spawn agent 在 task.cwd，读 task.skill，执行 task.ask
      POST /conclude {status, summary, session_ref, artifacts}
```

要点：
- **不暴露公网**（就是这个设计的意义）。
- 一台机器可以挂多个 worker（不同 agent / 不同能力），中台按 `to.agent` 路由。
- 进程崩溃 = lease 到期，中台自动重派，不需要人工介入。

### 3.2 Agent 运行时（我们目前的选择空间）

| 运行时 | 现状 | 适合 |
|---|---|---|
| `codex` CLI | ✅ 已装 0.154.0，已登录 | **MVP 首选**：`codex exec` 非交互跑，能改代码/跑测试 |
| Claude Code | ❌ 未装 | 复杂开发主力（文章首选），后续可加 |
| DSH 会话 | ✅ 本机可用 | 需要多轮/团队协作的复杂任务 |
| 浏览器操控 | ⚠️ 未接 | 无 API 的数据采集（GEO 巡检那类），后置 |

> 关键设计：**worker 不关心 Agent 是谁**。`to.agent` → 一个可插拔的 adapter。今天 codex，明天 claude，只改一行规则。
> 这正是文章说的"第一，接一种新事件特别简单；第二，换 Agent 特别简单"。

### 3.3 Skill = 给 Agent 的 SOP

每个任务类型配一个 skill 目录（规则 + 参考 + 脚本），规则里 `ask` 只给一句话："按 skill 里对应章节办"。

- **好处**：清晰、可控、可改。改业务只改 skill，不碰中台逻辑。
- **约束**：skill 必须是**能被 Agent 直接执行**的东西，不能是需要人解读的散文。
- 我们已有的 `videomod` Agent 循环、`docs/` 文档风格可以复用。

### 3.4 安全边界（必须一开始就有）

- Agent 在**指定 cwd / 临时 worktree** 里干活，不直接动主工作区。
- 密钥**不进 Agent 上下文**，只以环境变量名存在；审查 Agent 只读、无网、拿不到密钥。
- Agent 没有发布权——**只能开 PR**，后面交给 CI 中台。

## 4. 模块 C —— CI 中台（第二优先）

Agent 干到"开 PR"就结束，剩下五步全部机器化：

```
Agent 开 PR → ①审查 → ②完整检查 → ③合并 → ④发布 → ⑤线上核实 → 结果回写
```

### 4.1 五步的关键规矩（照抄，都是有原因的）

| 步骤 | 规矩 | 为什么 |
|---|---|---|
| ①审查 | **另一个模型**审，只读、无网、无密钥；**最多 3 轮**；只报真会出错的问题，不报风格 | 防"无限审查"（能审 10 轮改到天荒地老） |
| ②检查 | 类型检查 + 全部测试 + 构建 + 数据库只加不改等硬规矩 | 一条不过不许合 |
| ③合并 | 分支保护写死：没审过没检查过，**谁/什么工具都合不进主干** | 对 Agent 不信任，用机器强制 |
| ④发布 | 每次新开一次性环境，跑完连机器带身份一起删 | Agent 写的代码不在本机裸跑 |
| ⑤核实 | 发布完再去线上问一遍"跑着的版本是否包含本次改动" | 不看 CI 绿灯，看线上真实状态 |

### 4.2 我们的现实取舍

作者的 M4 自建 CI 解决的是**量**（AIHOT 一个月近 1000 个 PR，GitHub 免费 3000 分钟不够，超额 50 刀/月）。
我们现在没有这个量。

> **MVP：用 GitHub Actions + 分支保护 + 一个"审查 Agent"动作起步。**
> 等 PR 量上来（比如 >100 个/月），再考虑自建 runner（GitHub Actions self-hosted runner 也能跑在本机，比自建整套调度便宜）。

先做的是**规矩**（审查轮数上限、只读审查、分支保护、一次性环境），不是**机器**。

## 5. 模块 D —— 审批通道（"批奏折"）

### 5.1 交互形态：决策卡片 = 票拟

卡片必须包含三样东西，缺一不可：
1. **这是什么**（一句话 + 回原处的链接）
2. **Agent 的建议**（票拟：我建议这么办，理由是什么）
3. **可点的选项**（同意 / 拒绝 / 换个做法），点完即决策，卡片自己变成结论

### 5.2 什么才配推到我面前（白名单，硬编码）

只有这七类：

> 删数据 · 停服 · 花钱 · 对外发消息 · 改产品方向 · 新建/轮换密钥 · 修改权限

其余一律 Agent 自己做完上线，**不推送**。规则里 `tell: silent` 就是"别烦我"。

### 5.3 记忆资产（长期不被打扰的根本）

| 文件 | 内容 | 规则 |
|---|---|---|
| `定了的事.md` | 我亲口做过的决定 + 原话 + 日期 | Agent 遇到同类，直接照做，不再问 |
| `定了不做的事.md` | 我拒绝过的 | Agent 遇到，直接回绝，不再问 |

### 5.4 通道的降级方案

飞书自建应用 + 卡片消息是最爽的，但**不是第一步**。
MVP 可以先用**本地 Web 审批页**（中台自带一个 `/inbox` 页面），跑通"点一下 → 决策回流"的逻辑，再接飞书。通道可以换，**决策数据模型不能变**。

## 6. 范围裁剪：文章做法 vs 我们的 MVP

| 能力 | 文章做法 | 我们的 MVP | 理由 |
|---|---|---|---|
| 事件中台 | 自建独立服务（有网址有数据库） | ✅ **自建**：FastAPI + SQLite | 唯一必须自建的核心 |
| 定时任务 | 用 Claude/Codex 自带定时 | 中台内置 cron，接进事件流 | 统一入口，别分裂 |
| Agent 执行 | Claude Code / Codex / 云端 | ✅ codex CLI（已装）+ 可插拔 adapter | 零成本起步 |
| Skill | 每个任务一个 | ✅ 先做 1~2 个真实 skill | 有活才有 skill |
| CI | 自建 M4 虚拟机中台 | ⚠️ GitHub Actions + 分支保护 | 量不够，先立规矩 |
| 审批 | 飞书小卡 + 卡片 | ⚠️ 先本地审批页，再接飞书 | 先跑通闭环 |
| 浏览器操控 | GPT-6.1 Terra 操控 Chrome | ❌ 后置 | 复杂、易碎、非主线 |
| 可视化小镇 | 游戏化网页 | ❌ 后置（P3） | 爽感可以，别挡路 |
| 数据看板 | 中台数据库沉淀 | ⚠️ P2 简单统计页 | 先有数据再谈看板 |

## 7. MVP 路线图（建议，按周）

### P0 · 第一周：一条真实事件全自动跑通（最关键）

**目标**：让**一件真事**从"事件进来"到"结论落库"全程无人干预。

- 中台骨架：`POST /events`、`rules.json` 加载、去重、排队、`POST /lease`（长轮询 50s）、`POST /conclude`
- SQLite 三张表：`events` / `runs` / `decisions`
- 一个 worker：本机 Python 循环，调 `codex exec` 在指定目录跑 skill，回写结论
- 一个真实事件源（**先不接飞书**）：
  - 选项 A：GitHub Issue/PR webhook（需 `gh auth login`）
  - 选项 B：中台内置定时器，每天定时跑一次真实任务（如"扫一遍本周待办"）
- **验收**：事件进来 → 自动派单 → Agent 真跑了 → 结论和会话链接可在 `/runs` 查到

### P1 · 第二周：决策闭环 + 噪声抑制

- 本地 `/inbox` 审批页（或直接上飞书卡片）：决策 → 生成新事件回流 → Agent 继续
- `tell: needed/silent` 生效：silent 的事绝不进 inbox
- `定了的事.md` / `定了不做的事.md` 落地，接入 Agent 的 system prompt
- **验收**：一周内 inbox 被推送 ≤ 10 条，且每条都值得推

### P2 · 第三、四周：审查 + 多 Agent 路由

- 第二个模型做**只读审查**（最多 3 轮，只报真错）
- 分支保护 + 一次性环境跑测试
- 多 worker / 多 agent 路由（codex / claude / DSH），按规则分配
- 简单统计页（事件量、成功率、平均耗时、上报率）

### P3 · 之后（想清楚再做）

- 可视化流水线（天气/时间打通那种）
- 浏览器操控类事件源
- 飞书深度集成（卡片交互、AI 助理）
- 自建 CI runner（等量上来）

## 8. 主要风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| **边界设计失控**（最大风险） | 上报太多 → 飞书刷屏 → 又回到"人盯"；或上报太少 → Agent 乱权 | 白名单（七类）+ `tell` 字段 + 决策资产沉淀；**宁先多报** |
| 重复派单 / 互相覆盖 | 同一件事多 Agent 同时干 | `idempotency_key` + 同 `subject` 串行 + `parallel` 上限 |
| 重试风暴 | Agent 挂了一堆任务同时重试 | 重试 ≤3 + 指数退避 + 熔断 |
| Agent 无法无天 | 乱改代码、误删 | 临时 worktree + 分支保护 + 只读审查 + 无密钥 |
| 成本失控 | token 烧超 | 每事件 token 预算 + 模型分级（贵模型只给复杂活） |
| 中台单点 | 服务挂了全停 | MVP 接受；加健康检查 + 降级（退回定时任务）；SQLite 有备份 |
| 长轮询挂死 | worker 卡住不领活 | lease TTL + 心跳 + 监控"最长未领活时间" |

## 9. 需要你拍板的 5 个问题

1. **第一个真实事件源选哪个？**（GitHub Issue/PR webhook / 定时任务 / 飞书消息 / 邮件）
   —— 决定 P0 做什么。
2. **中台跑在哪？**（本机常开 Mac / 家里的机器 / 云服务器）
   —— 决定用拉模式还是推模式。
3. **Agent 先用谁？**（codex CLI 已装，最快 / 装 Claude Code / 用 DSH）
4. **审批通道：先本地网页，还是直接上飞书？**
   —— 飞书要自建应用 + 权限，约半天到一天起步。
5. **这套只给你自己用，还是要成为可复用到所有项目的底座？**
   —— 决定要不要一开始就做多项目/多租户抽象（建议：**先单项目跑通，架构上留扩展点**）。

## 10. 与现有项目的关系

- 工作区里已有 `appeal-insight`（Next.js 业务系统 + `videomod` Agent 循环），其"模型节点可配置 / Agent 循环 / 交付物结构"的经验可直接复用。
- 本中台定位是**外挂的操作系统**：不属于任何一个业务项目，但将来所有业务项目的自动化都挂在它下面。
- 因此建议**独立目录、独立仓库、独立数据库**，不混进业务项目。
