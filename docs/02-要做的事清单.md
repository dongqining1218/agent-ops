# 02 · 要做的事清单（完整 WBS）

> 回答一个问题：**这个项目从头到尾，具体要做哪些事？**
> 每一项都标了：做什么、为什么要做、产出什么、大概多久、依赖谁。
> 说明：只写"要做的事情"，不写代码细节；细节在后续每份设计文档里展开。

---

## 0. 先解释 4 个词（大白话版）

看懂清单需要先认识 4 个词，用生活里的东西打比方：

| 词 | 大白话 | 打比方 |
|---|---|---|
| **事件源** | 告诉系统"有事发生了"的地方 | 门口的**报事人**：有人来敲门说"出事了" |
| **中台** | 一个 7×24 的调度员，统一收事、分派、催办、记账 | **传达室 + 调度员** |
| **worker（接单程序）** | 挂在一台机器上等活的程序，领到活就去叫 Agent 干活 | **等单的师傅** |
| **skill** | 给 Agent 看的作业指导书 | **岗位 SOP 手册** |
| **审批卡片** | 需要你决定时，递到你面前的一张卡片，点一下就行 | **票拟 → 批红** |

**什么是"事件源"？** —— 就是这套系统"什么时候会被叫醒"。
没有事件源，中台就是个空转的调度员。常见的几种（举你我身边的例子）：

- **定时**：每天早 9 点，让 Agent 去检查一次 GitHub 仓库有没有新 PR / 有没有过期的待办
- **GitHub**：有人给仓库提 Issue、开 PR、流水线挂了，自动来一条
- **飞书/微信**：群里有人 @ 你、有人提了意见，自动来一条
- **邮件**：收到某类邮件，自动来一条
- **告警**：服务器报错，自动来一条

> 我们的第一步只需要**任何一种**真实事件源就够了，先跑通一条链路，不是一次全接。

## 3. 阶段 1：中台跑通一条真实链路（核心，5~7 天）

**验收目标：一件真的事情发生 → 自动分派 → Agent 真干活 → 结论落库可查。中间没人管。**

### 3.1 中台骨架（后端服务）

| 编号 | 要做的事 | 说明 | 产出 | 预估 |
|---|---|---|---|---|
| T1-1 | 服务骨架 + 配置文件 | 一个能起来的 HTTP 服务，读配置、连 SQLite | 服务能启动、`/health` 通过 | 0.5 天 |
| T1-2 | 数据库表设计 | `events`（事件）、`runs`（一次运行）、`decisions`（决策）三张表 + 索引 | 建表脚本 | 0.5 天 |
| T1-3 | 统一事件格式 + 接入接口 | `POST /events`，把各种来源压成统一 6 字段 | 接口 + 校验 | 0.5 天 |
| T1-4 | 鉴权（最简单版） | 每台机器/每个来源一个 token，防止误发 | token 校验 | 0.2 天 |
| T1-5 | **去重** | 同一个 `idempotency_key` 只处理一次；同 `subject` 默认串行 | 唯一索引 + 时间窗 | 0.5 天 |
| T1-6 | 规则文件 + 匹配 | `rules.json`：什么来源什么类型 → 交给谁、哪个目录、哪个 skill、并发数、要不要找我 | 规则加载/校验/匹配 | 0.5 天 |
| T1-7 | 队列与并发控制 | 排队；同组并发上限（比如最多 3 条同时跑） | 队列逻辑 | 0.5 天 |
| T1-8 | **长轮询领活接口** | `POST /lease` 挂 50 秒，没活就再挂；有活立领取 | 领活接口 | 0.5 天 |
| T1-9 | 结论回写接口 | `POST /conclude` 写状态/摘要/会话链接/产物，幂等 | 回写接口 | 0.3 天 |
| T1-10 | 超时、重派、失败上报 | lease 到期回收；失败重试 ≤3 次 + 退避；连续失败/掉线 → 上报 | 状态机完整 | 0.5 天 |

### 3.2 执行侧（worker + Agent + skill）

| 编号 | 要做的事 | 说明 | 产出 | 预估 |
|---|---|---|---|---|
| T1-11 | worker 接单程序 | 本机常驻循环：领活 → 干活 → 回写；崩溃自动恢复 | 一个可后台跑的程序 | 0.5 天 |
| T1-12 | Agent 适配器（先用 codex） | 在指定目录、带指定 skill 启动 `codex exec`；拿回结果和会话引用 | adapter 接口 + codex 实现 | 0.5 天 |
| T1-13 | 第一个真实 skill | 选一件真事写成 SOP（见下方"第一件真事"建议） | 1 个 skill 目录 | 0.5 天 |
| T1-14 | 查询/观察页面 | `/runs` 列表：每条事件的状态、耗时、结论、跳回会话 | 一个简单网页 | 0.5 天 |

### 3.3 "第一件真事"建议（T1-13 的内容）

三选一，按"真实 + 简单 + 有重复价值"排序：

| 候选 | 具体做什么 | 难度 | 价值 |
|---|---|---|---|
| **A. 每日仓库巡检** | 定时每天早 9 点：扫 `appeal-insight` 仓库的未处理 Issue / 过期 PR / 构建失败，汇总成一张卡片 | ⭐ 最低 | 立刻有用，且是纯只读，零风险 |
| B. 每日待办汇总 | 定时扫一组固定来源（文件/网页），生成当天待办 | ⭐⭐ | 一般 |
| C. GitHub 事件驱动 | 有人开 PR/提 Issue 立刻叫醒 Agent 处理 | ⭐⭐⭐ | 高，但需 `gh auth login` + 先有 CI 规矩 |

> **推荐 A**：只读、定时、每天都能验证，且不需要任何外部账号。

**阶段 1 验收**：连续 3 天，每天早上自动生成结果，`/runs` 里能看到完整记录，且**你没有手动做任何事**。

## 4. 阶段 2：审批闭环"批奏折"（3~4 天）

**验收目标：一件需要我决定的事，变成一张卡片，我点一下，它自己继续干完。**

| 编号 | 要做的事 | 说明 | 产出 | 预估 |
|---|---|---|---|---|
| T2-1 | 决策数据模型 | 决策 = 事件 + 建议 + 选项 + 我的选择 + 时间 + 原话 | 表结构 + 接口 | 0.5 天 |
| T2-2 | 决策卡片生成 | Agent 输出约定格式（含建议/理由/选项）→ 中台转成卡片 | 卡片渲染 | 0.5 天 |
| T2-3 | 审批入口（本地 inbox 页面） | 列出待决策项，点同意/拒绝/其他 | 一个页面 | 0.5 天 |
| T2-4 | 决策回流成新事件 | 我点完之后，中台生成一条新事件，把等待的 Agent 叫醒继续 | 闭环接口 | 0.5 天 |
| T2-5 | `tell` 字段生效 | `needed` 才进 inbox；`silent` 一律不打扰 | 规则生效 | 0.2 天 |
| T2-6 | 上报白名单 | 只有 7 类事能推给我：删数据/停服/花钱/对外发消息/改产品方向/密钥/权限 | 白名单硬编码 | 0.2 天 |
| T2-7 | 决策记忆库 | `定了的事.md` / `定了不做的事.md`（原话 + 日期），注入 Agent 提示词 | 两个文件 + 注入逻辑 | 0.5 天 |
| T2-8 | 上报降噪验收 | 统计一周推送条数，目标 ≤10 条/周 且每条都值得 | 统计 | 0.3 天 |
| T2-9 | 通知（可选，先不做飞书） | 先用本地页面 + 系统通知；飞书放阶段 4 | —— | 0 |

## 5. 阶段 3：CI 质检链路（4~5 天）

**验收目标：Agent 写完代码只能开 PR，自己绝对不能上线；审查不过/测试不过就合不进去。**

| 编号 | 要做的事 | 说明 | 产出 | 预估 |
|---|---|---|---|---|
| T3-1 | PR 产出规范 | 约定 Agent 交付物：分支名、PR 模板、改动说明、验收自测 | 模板 + skill 里写明 | 0.3 天 |
| T3-2 | 只读审查 Agent | 用第二个模型审，**只读、无网、无密钥、只报真错不报风格** | 审查 adapter | 1 天 |
| T3-3 | 审查轮数上限 | 最多 3 轮，超了就上报人，防止无限审查 | 计数逻辑 | 0.3 天 |
| T3-4 | 一次性检查环境 | 每次在临时 worktree / 临时目录跑测试，跑完就删 | 检查脚本 | 1 天 |
| T3-5 | 分支保护 | GitHub 设置：没审查通过、没检查通过，谁都不能直接合主干 | 仓库设置 + 文档 | 0.3 天 |
| T3-6 | 合并 / 发布触发 | 检查通过自动合并；发布用现成 GitHub Actions 或简单部署脚本 | 流水线 | 0.5 天 |
| T3-7 | 线上核实 | 发布完去线上问"版本里有没有这次改动"，结果回写 PR | 核实脚本 | 0.5 天 |
| T3-8 | 交付结果回写 Agent | Agent 看一眼 PR 就知道最终状态（合了/没合/卡在哪） | 回写逻辑 | 0.3 天 |

> 取舍说明：作者自建了整套 CI（因为一个月近 1000 个 PR、GitHub 分钟数不够）。
> 我们的 PR 量远没到，**先用 GitHub Actions + 分支保护把"规矩"立起来**，机器不上。等月 PR 过百再说自建。

## 7. 横切工作（贯穿全程，不是单独阶段）

| 项目 | 内容 | 什么时候做 |
|---|---|---|
| 安全边界 | Agent 只在指定目录/临时 worktree 干活；密钥不进上下文；审查只读 | 阶段 1 就开始 |
| 成本控制 | 每条规则设 token 预算；贵模型只给复杂活 | 阶段 2 |
| 可观测 | 每条事件的完整链路留痕（谁派的、跑了多久、结论、失败原因） | 阶段 1 |
| 数据备份 | SQLite 每日备份到本地/私有仓库 | 阶段 1 末 |
| 文档 | 规则怎么写、加新事件怎么加、加新 Agent 怎么加 | 每阶段末各 1 页 |
| 降级预案 | 中台挂了怎么办（退回定时任务手工跑）；worker 挂了怎么发现 | 阶段 2 末 |

## 9. 每个阶段的"停手判断"

| 阶段 | 如果…… | 就停下来别往下做 |
|---|---|---|
| 1 | 用了 3 天，没觉得省事 | 先改第一件真事选错了，别加功能 |
| 2 | 一周推给我 >20 条 | 白名单/规则没设计好，回去改，别上更多事件源 |
| 3 | Agent 产出质量本来就高、很少出错 | CI 可以只保留"分支保护 + 测试"，审查后置 |
| 4 | 可视化/飞书只是爽 | 想清楚谁看、看了干嘛，否则不做 |
